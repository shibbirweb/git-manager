Docs are deferred; these are the wiki changes the O3 work needs. No menu labels, settings or shortcuts changed. Nothing looks different on screen, so no screenshots need retaking. Verify every name below against the code when writing.

## Developer pages to update

- `docs/wiki/developer/How-the-Files-Panel-Works.md`
  - Mermaid at lines 20-21: `listDirectory(folder.root, relative dir, repoRoots)` / `list_directory` is gone. Now `loadDirs(dirPaths)` groups folders by workspace folder (`groupByFolder` in `folderListings.ts`) and sends one `listDirectories(root, dirPaths[], repoRoots, known)` per workspace folder; `list_directories` answers a `FolderListing[]` (`dirPath`, `stamp`, `unchanged`, `entries`, `truncated`, `error`). Answers are applied once (`applyAnswers`): unchanged folders and equal listings keep their arrays, collections are copied only on change, a per-folder request number drops answers a newer request replaced.
  - New section "Stamps": the backend's `FolderLister` (`src-tauri/src/git/files.rs`) opens each owning repository once per call and looks at each `.gitignore` once. A folder's stamp is a hash of: the folder's own stat (mtime, size, inode, ctime), the repository roots right inside it, the owning repository root, its `info/exclude` and the per-user ignore file (`core.excludesFile` or `~/.config/git/ignore`, path and stat), and the `.gitignore` of every folder from the repository root down. Known stamps (`knownStamps`, only for folders still loaded) make unchanged folders answer `unchanged` without reading them. Measured on this repository (release build), 40 folders in the new format (no `path` per entry): 40 unbatched calls 13-27 ms and 41 KB, one batched call 5.9 ms and 41 KB, one stamp check with every folder unchanged 0.36 ms and 4 KB. The old `list_directory` also sent a `path` per entry (the audit estimated about 0.6 MB for 40 folders in a big repository).
  - The double re-list after an in-app file operation: `afterWrite` lists the touched folders at once, then the watcher's `listingVersion` refresh sends their new stamps and every folder answers `unchanged` (no folder is read). Kept on purpose: the same watcher batch may hold other changes.
  - `DirEntry` lost `path` (the frontend joins `dirPath` and `name`); `TreeEntry` moved to `folderListings.ts`.
  - Tones: `tones`, `marks`, `deleted` maps were rebuilt for every status change of every repository. Now `repoTones(status, repoRoot)` (`tones.ts`) caches tones, marks and deleted files per status object in a WeakMap (an unchanged status keeps its object), and `workspaceTones` answers lookups over the repositories without merging (strongest tone, last repository's mark, deleted lists in repository order). `tonesByPath` stops walking up as soon as a folder already has an equal or stronger tone. Tested against the old functions on random data.
  - LFS badges follow `repoStore.treeVersions` now (see LFS below).
  - Code table at line 86: `commands/files.rs` has `list_directories` and `read_worktree_file`; add `folderListings.ts`.
  - Tests at line 123: `list_directories_sorts_folders_first_and_marks_ignored_entries`, `list_directories_refuses_paths_outside_the_work_tree_per_folder`, `list_directories_answers_unchanged_until_something_the_listing_depends_on_changes`, `list_directories_uses_the_deepest_repository_for_ignores`, plus `folderListings.test.ts` and the random tests in `tones.test.ts`.

- `docs/wiki/developer/How-Git-LFS-Works.md`
  - Mermaid at lines 32-38 and the paragraph at line 108 ("Read per refresh, not per file"): the store no longer follows the status object. `repoStore.treeVersions[root]` is bumped on watcher events with refs, index, structure or the new `attributes` flag (`refreshPlan.treeChanged`), on Refresh All, after every `repoStore.run` git operation and in the write fallback; `lfsStore.follow(repoRoot, treeVersion)` checks only when it moved. ## Bugs we fixed (drafts)

### How-File-Operations-Work.md: "a//b" created a nested file the dialog would refuse

- Issue: the New File dialog refused "a//b" and "a/" ("Each part between slashes needs a name"), but the backend (used by MCP `create_file` and anything else that calls `file_create`) dropped the empty parts and created `a/b`, so the two sides disagreed about what is a valid name.
- Why: `split_new_path` filtered empty parts out instead of refusing them, and nothing tied the two rule sets together.
- Fix and why: the backend refuses empty and blank parts with the dialog's message, and both sides now run one case table (`nameRules.cases.json`), so a rule cannot drift again without a test failing on one side.

### How-File-Operations-Work.md: names over 255 bytes failed late, and MCP counted characters

- Issue: the dialog refused names over 255 bytes, but the backend let them through to the file system, which failed with a raw OS error; the MCP `rename_path` tool capped 255 characters, so "é" x 128 (256 bytes) passed its check and then failed.
- Why: the byte limit lived only in `fileNames.ts`.
- Fix and why: `validate_name` refuses more than 255 bytes with "The name is too long", and `rename_path` uses `nameBytes`; bytes are what APFS and ext4 limit.

### How-File-Operations-Work.md: a case-only clash passed the dialog on macOS

- Issue: on macOS, New File "Cart.ts" in a folder with "cart.ts" passed the dialog and then the backend refused it ("already exists").
- Why: `nameProblem` compared names exactly, while APFS ignores case.
- Fix and why: `nameProblem` takes `ignoreCase` (macOS and Windows) and names the entry already there; a case change of the current name stays allowed, since the backend renames that through a temporary name.

### How-File-Operations-Work.md: the drop clash check listed closed folders and compared string paths

- Issue: dropping onto a closed folder listed the whole folder just to check names, and the check compared string parents, so a symlinked path could disagree with the backend's canonical one.
- Why: `moveClash` ran in the frontend on a listing.
- Fix and why: `file_move` with `dryRun` runs the backend's own plan (`checked_move_plan`) and returns the clashing name; one rule, one place, no listing.

### How-the-Files-Panel-Works.md: every refresh read every open folder again

- Issue: with many folders open, each refresh (after a save that added a file, a branch switch) sent one call per open folder and re-read all of them, and an in-app file operation re-listed them twice.
- Why: listings had no way to say "unchanged", and each folder was its own call that opened its repository again.
- Fix and why: one `list_directories` call per workspace folder with stamps; unchanged folders answer in about 100 bytes, so the second re-list after an in-app write costs only stats. The stamp covers everything the listing depends on (entries, nested repositories, every ignore input), so it cannot hide a real change.
