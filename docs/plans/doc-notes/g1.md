## Developer chapter: developer/How-Line-Staging-Works.md (new, about 900 words)

### Why we need it
Commits that tell one story: stage part of a hunk (GitHub Desktop, VS Code "Stage Selected Ranges",
JetBrains partial staging). The existing chunk arrows only move whole hunks (and write the full side
with `stage_content`).

### How it works
Mermaid sequence:
```
DiffView (selection) -> lineSelection.ts selectedChangeLines(hunks, side, spans) -> LineSelection {oldLines, newLines}
-> changesSelection.applyLines (confirm for discard, deleted file -> whole file dialog)
-> repoStore.run -> api.applySelectedLines (one IPC call: repoPath, filePath, origPath, action, selection, knownVersion)
-> Rust commands/lines.rs: conflict check, version check (working_file_version), read sides with git2
-> git/partial.rs partial_text (desired text) -> unified_patch -> git apply --check -> git apply (stdin)
-> refresh; Discard returns the patch -> toast Undo -> restore_discarded_lines (git apply --check, git apply)
```
Mermaid flowchart for the per-action table:
| action  | diff (old -> new)      | patched side | patch                    | git                                   |
| stage   | index -> work tree     | old (index)  | index -> desired         | `git apply --cached`                  |
| unstage | HEAD -> index          | new (index)  | desired -> index         | `git apply --cached --reverse`        |
| discard | index -> work tree     | new (work)   | desired -> work tree     | `git apply --reverse`                 |

Key points:
- Line coordinates: the same as the diff view (LF-normalized text split on `\n`, `line_diff::hunks`
  with imara-diff), so a selection names the same lines in Rust. The raw texts keep their bytes:
  `SideLines` strips one `\r` per line for comparing and remembers each line's ending.
- `partial_text`: walk the hunks; outside them copy the patched side; inside a hunk walk the patched
  side and the other side by offset: an unselected patched line stays, a selected one goes; a selected
  other-side line comes in. So a selected replacement takes the place of the line it replaces. Lines
  copied in keep their own ending when both sides use the same convention, else take the patched
  file's (an LF index with a CRLF work tree under autocrlf stages LF lines).
- Then the patch is simply the unified diff from the patched text to the desired text
  (`unified_patch`, 3 lines of context, hunks merged like git, `\ No newline at end of file`,
  C-quoted names like git, a tab after names with a space). Building the desired text first and diffing
  it is what makes missing final newlines and CRLF exact: the patch always fits the bytes in the index
  or the work tree.
- New file (no index entry): a `new file mode` patch from /dev/null with the work tree's mode (100755
  for executables). Unstaging every line of a newly added file: a new-file patch applied in reverse,
  which removes the index entry (the file is untracked again). Intent-to-add entries (`git add -N`)
  read as an empty file and work as a normal modification.
- Safety: `--check` first, then the same apply; `--whitespace=nowarn` so `apply.whitespace=error`
  never refuses a user's trailing space. The diff's `version` is checked first: a stale selection is
  refused, nothing applied.
- Refused: deleted side, conflicts (index stages 1-3), binary, LFS pointer, symlink, submodule,
  over 4 MB.
- Frontend: `lineSelection.ts` (pure): `rangeLines` (a range ending at a line start leaves that line
  out; an empty range is its line), `selectedChangeLines` (pairing by offset, rest of the other side at
  a hunk's end, zero-line changes picked when the selection touches them), `mergeRanges`,
  `selectionSize`. DiffView tracks the active side (last user selection or focus) and counts the picked
  lines in a requestAnimationFrame after selection changes (buttons enable). Hunks are dropped after a
  chunk arrow changed a side (until the reloaded diff arrives), so no stale line numbers are sent.
- Menu: `diffLines.svelte.ts` holds the DiffView on screen that offers line actions (attach/detach in
  an effect); `menuState.ts` gets `diffLines` ("unstaged" | "staged" | null) from `appMenu.svelte.ts`;
  `menuActions.ts` runs `diffLines.run(action)`. Keys are menu accelerators, so custom shortcuts apply.
- Toasts got an optional action button (`ToastAction`, `toast.successWithAction`, `toast.runAction`).
  The discarded patch lives only in the toast's closure (memory: freed when the toast closes).

### Design decisions
- Editor selection instead of GitHub Desktop style gutter checkboxes: the MergeView already owns both
  gutters and the revert column; a selection works with the keyboard, multiple cursors and both sides,
  and needs no extra state that could drift from the diff. Checkboxes can come later.
- Desired text, then a fresh diff, instead of editing hunk lines into a patch by hand: one simple
  rule set, and the patch always matches the bytes it is applied to.
- `--reverse` for unstage and discard (like `git reset -p` / `git checkout -p`): the same patch,
  applied forward, is the Undo of a discard.
- Version check instead of re-deriving the selection: cheap, and a changed file is never patched at
  the wrong lines.
- Deleted files: no partial deletion; the dialog offers the whole-file action (existing commands).
- Discarding every line of an untracked file leaves an empty file (no delete), so the action never
  removes a file.
- Keys macOS only, like the rest of the Git menu (Ctrl+Alt is AltGr on many Windows layouts).
