Docs are deferred; these are the wiki changes the O2 work needs. No user-facing labels, settings or shortcuts changed.

## Bugs we fixed (drafts)

### How-Diffs-Work.md: a big file's diff showed one giant change
- Issue: in a long file with a handful of edits far apart, the diff view highlighted almost the whole file as one change, and F7 found only one change.
- Why: MergeView uses CodeMirror's character diff with `scanLimit: 500`; past that many changed characters in a scanned range it falls back to a crude diff that merges everything between the first and last edit. Without the limit the result is right but costs about 113 ms at 20k lines and 400 ms at 100k on the main thread.
- Fix: the backend already reads both sides, so it now adds line hunks from imara-diff (histogram, git's slider heuristics) to every `FileDiff`. DiffView gives MergeView a `diffConfig.override` that maps each hunk to its character range and runs CodeMirror's diff only inside it (1.7 ms at 20k, 5.8 ms at 100k, with the right number of changes). Chosen because it is correct and cheap at once and keeps CodeMirror's word-level highlights; other inputs fall back to CodeMirror's own diff.

### How-the-Editor-Works.md: every refresh reloaded every open tab
- Issue: saving a big file made the app busy for a moment, and each status refresh (any change in the repository) re-read every open tab, fetched its HEAD and index texts and ran `git blame` again: about 37 ms, 7.8 MB over the bridge and 3 blames per save of a 20k-line file, and 15 ms plus 3.2 MB for each other open tab.
- Why: the tab's status effect called `load(true)`, which always read the whole file, then `loadHead()`, which always fetched `get_file_diff("staged")` (both HEAD and index texts) and re-blamed.
- Fix: versions. The file read takes the version the tab already shows and answers `unchanged` from a stat; Save gets the new version back; marks and blame remember the text (CodeMirror `Text` identity) and HEAD (blob id for marks, commit id for blame) they were made for and run only when one changed. Chosen over a frontend cache or watcher-provided paths because it is stateless in Rust ("no persistent backend caches") and works for every refresh source.

### How-Editor-Features-Work.md (or How-the-Editor-Works.md): typing lagged in large files
- Issue: each key in a 20k-line file cost several ms of our own work (tens of ms at 100k), and the first word completion took 35 to 200 ms.
- Why: the conflict-marker field rescanned the whole document per edit with `doc.line(i)`; the change gutter rebuilt its RangeSet whenever the document changed; `completeAnyWord` scanned the whole document per word start and stops caching after 2000 words; change marks ran a JS Myers diff that kept a full copy of its V array for every step (60+ MB spikes).
- Fix: conflict scan only when an edited line looks like a marker (else the same array or shifted regions); the gutter maps its markers through edits; completion reads a window of lines around the cursor with a cap; marks moved to Rust; the remaining JS Myers diff (line history) keeps only the 2d+1 diagonals it reads back. Chosen because each is exact (randomized tests compare with the full computation) and keeps the work proportional to the edit, not the file.

### How-the-Merge-Tool-Works.md (small): each side was held three times
- Issue: memory of the merge tool grew with three copies of each side.
- Why: the side text was in the document prop, in the side editor and again as an array of lines for applying chunks.
- Fix: apply and the word highlights read the side editors' own documents; the base is sliced from its string through a compact line-start index.
