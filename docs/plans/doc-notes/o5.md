## 2. Search Everywhere All tab: Classes and Members cancelled each other

`docs/wiki/developer/How-Search-Everywhere-Works.md`: where queries "stop when a newer one starts",
say the symbol queries keep one latest-query counter per scope (`SymbolScope::index`,
`Shared::symbol_seq` array in file_search.rs). Tests list: add
`the_all_tab_classes_and_members_queries_do_not_cancel_each_other` in `src-tauri/src/symbols/tests.rs`.
No public API change (`query_symbols` signature unchanged).

Bugs we fixed draft:
- Issue: on a big workspace the All tab often showed no Classes section (the Classes tab was fine).
- Why: the All tab sends a Classes query and a Members query at the same time. Both bumped one
  shared `symbol_seq`, and a running symbol search stops when the counter moves, so the second
  query made the first return empty.
- Fix: one counter per scope, so only a newer query of the same scope stops a search. Chosen over
  one combined query because it is a two-line change, keeps the IPC shape the command palette
  reuses, and each scope still cancels its own stale queries.
The "2 classs" text was already fixed earlier (countLabel.ts, 609288e); nothing to write.

## 3. Preview scheme: git blobs ignore Range

`docs/wiki/developer/How-the-Preview-Scheme-Works.md`:
- "Ranges" (lines ~53-62): ranges apply to work tree files only. A revision (blob) request always
  gets 200 with the whole blob; `Range` is ignored and no `Accept-Ranges` header is sent, so
  WebKit never asks for pieces. "Every answer has Accept-Ranges" -> only work tree answers.
- Line ~68: "answers its range and drops it" -> sends it whole and drops it.
- Line ~97 tests: "blob ranges" -> `a_blob_is_always_sent_whole`.
- Mermaid sequence at line ~26 ("GET, maybe with Range"): note Range only for worktree.

Bugs we fixed draft:
- Issue: opening a big PDF from history (a commit, HEAD or the index) used a lot of CPU.
- Why: the scheme offered `Accept-Ranges`, so WebKit's PDF viewer read the file in 4 MB ranges.
  A blob is stored compressed and can only be read whole, so each range inflated the whole blob:
  a 100 MB PDF meant 25 full inflates.
- Fix: blob answers ignore `Range` and offer none; the blob is inflated once. Work tree files keep
  ranges because they are read by seek. Chosen over caching inflated blobs because the app keeps
  no backend caches (memory is a feature) and the one-piece limit (100 MB) already applies.

## 4. Rich Markdown editor sync is incremental

`docs/wiki/developer/How-the-Rich-Markdown-Editor-Works.md`:
- Sequence diagram (line ~25) and "On load" (line ~36): the load reuses the parser's own tree: the
  remark plugin `gmBlockRanges` (registered before commonmark so it runs first) records the
  top-level ranges of the text Milkdown parsed, so loading needs one parse, not two.
- Sync: `serializeBlocks` keeps a `WeakMap<ProseNode, string>` (`written`): ProseMirror reuses
  untouched nodes, so only edited blocks are serialized. After writing the edit, `rangesAfterEdit`
  (richSync.ts) shifts ranges after the edit and parses only the edited stretch plus the untouched
  block on each side; when those context blocks do not read back where they were (an unclosed
  fence, two lists joining), it returns null and a full parse runs.
- "Edit the page, keep the file" decision (line ~81): no longer "a parse per edit" of the whole file.
- Tests: new `src/lib/markdown/richRanges.test.ts` (real remark + remark-gfm, the parser Milkdown
  uses): ranges match a full parse after edits, inserts and deletes anywhere; untouched blocks
  byte for byte; only the stretch is parsed in a long text; fallbacks for an open fence and joined
  lists; 400 seeded random edits always equal a full parse.
- Possible mermaid: flowchart "edit -> serialize changed nodes (WeakMap) -> blockEdit -> applyEdit ->
  rangesAfterEdit -> context blocks match? yes: splice ranges / no: full parse".
- Measured (5,040-line, 309 KB Markdown, Playwright WebKit): sync per pause median 690-1070 ms
  -> 1-2 ms (max 6 ms); load 1.5-2.6 s -> 0.75-1.6 s; output byte-identical.

Bugs we fixed draft (or a "Performance" note):
- Issue: typing in Preview Only on a big Markdown file paused the app after every short stop.
- Why: every sync serialized every block and parsed the whole file again to find block ranges.
- Fix: cache serialized blocks per node and update ranges by parsing only the edited stretch,
  checked against the neighbors with a full-parse fallback. Chosen because it keeps the exact
  block-by-block write back (unchanged blocks stay byte for byte).
