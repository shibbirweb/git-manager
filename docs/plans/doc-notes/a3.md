## User page outline: usage/Windows.md (about 500 words)

- What a window is: each window shows one folder or workspace (or the welcome screen), with its own
  tabs, terminals, Changes, Log and Files panel. Like VS Code's New Window or JetBrains' "open in new window".
- Opening a window:
  - File > New Window (Shift+Cmd+N): an empty window with the welcome screen.
  - File > Open Folder in New Window...
  - Welcome screen: Cmd+click a recent folder or workspace (Ctrl+click on Windows and Linux), or
    right-click it > Open in New Window. Hover text: "Cmd+click to open in a new window".
  - The workspace name menu in the header: New Window, Open Folder in New Window..., Open Recent in New Window.
- Already open: opening a folder that another window shows brings that window to the front instead
  (any way of opening: Open Folder, recent, workspace file). Rule: one folder matches a window that has
  it among its folders; several folders match a window with exactly those folders; a workspace file
  matches the window showing that file.
- Switching: the Window menu lists every window by its title (the workspace name). Cmd+` cycles (macOS).
- Closing: File > Close Window (Shift+Cmd+W) or the red button; asks first when a tab has unsaved
  changes. Closing the last window quits the app.
- Quit and start again: Settings > Layout > **Reopen windows on start** (on by default) reopens every
  window with its folders, size and position, each with its own tabs (Reopen tabs on start). Off:
  one window with the last folders you had open. A folder given on the command line opens only that folder.
- Settings changed in one window apply to every window right away. Panel sizes and which panels are
  open stay per window.
- Memory: each window adds one web content process (the status bar memory readout counts all windows
  together). Closing a window frees its watchers, terminals and search indexes.
- git mergetool always uses one window (no New Window there).

## Developer chapter outline: developer/How-Windows-Work.md

Why: users work on several projects at once; one process keeps memory low (one backend, one MCP
server, one git console), each window adds only a web view.

How it works (mermaid ideas):
1. sequence: File > New Window -> `window_open` -> owner check (`WindowBook::owner`) -> focus existing
   or `WebviewWindowBuilder` (label `window-N`, cascade +28) -> new page -> `window_startup` ->
   `WindowStart::Open` -> openFolders -> `window_set_workspace` (title, preview folders, MCP windows,
   session write).
2. flowchart of event routing: watcher (owns label) -> `emit_to(webview_window(label))`; git-progress ->
   `emit_for_path` (windows_for_path, else broadcast); config-changed -> `emit_filter` (all but sender);
   mcp-ui-request -> `pick_window` target; git-command and mcp-activity broadcast.
   Frontend listens with `listenHere` (target WebviewWindow) because a plain `listen` (target Any) hears
   every emit_to.
3. state diagram of the session: window opened -> reported -> closed (removed unless last) ; quit
   (`RunEvent::Exit` / `ExitRequested{code: Some}`) -> `quitting` flag -> session saved from the book.
4. sequence of a settings save across windows: diffJson -> `update_config` (lock, re-read, apply,
   atomic write) -> `config-changed` -> `rebaseIncoming` in the other windows.

Design decisions:
- Ownership by canonical paths kept in Rust (the book), so every open path (menu, recent, workspace
  file, MCP UI tool) uses the same rule; a window still loading owns its intent (`expected`).
- One settings writer: re-read before write with a merge. Each window sends key-path patches
  (set/remove, null is a value: keybindings use null). Chosen over "one window writes" because every
  window changes settings; chosen over RFC 7386 merge patch because null must stay a value.
- Per-window layout keys (`WINDOW_STATE_KEYS`) are not taken from other windows.
- Menu: built per window in JS; macOS has one menu bar, so the focused window re-asserts its own
  (`setAsAppMenu` + `setAsWindowsMenuForNSApp` + help) on focus; clicks reach the window whose page
  built the item, and enabled/checked state follows it. Windows/Linux: `setAsWindowMenu`.
- MCP: one server; tools reach the union of all windows' folders; UI tools go to the window holding
  their path argument (deepest folder), else the last focused window (tracked from `Focused(true)`,
  because the app is usually not frontmost while an agent calls it). `take_screenshot` takes the last
  focused window. `list_workspace` returns `windows` with label, title, focused, folderPaths.
- Session written by the backend only (`state.json` key `windows`), write-through on workspace change
  and close, plus at quit. Closing the last window keeps it (closing it quits the app). Cmd+Q ends the
  loop without Destroyed events, so the book still has every window at `RunEvent::Exit`.
- Labels `window-N` never reused in a run (late events of a closed window cannot reach a new one).
- Update check and What's New only in the `main` window; MCP and memory log configure from every
  window are idempotent.
- Git Console stays app-wide (broadcast `git-command`, one ring buffer).

Bugs we fixed while building it (for the chapter's "Bugs we fixed"):
- A second window's start (`terminalStore.init` -> `terminal_close_all`) would have killed every
  shell of the first window. Now terminals have an owner and close_all closes only the caller's.
- Find in Files ids are counted per page; one FileSearch for all windows would refuse the window
  with the lower counter. Now one FileSearch per window.
- `listen()` defaults to target Any, which hears every `emit_to`; window events use `listenHere`.
