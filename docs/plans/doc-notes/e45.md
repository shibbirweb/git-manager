## User page: usage/Compare-Files.md (outline)

1. What it is: a read-only diff of any two files, not only versions of one file. Opens in its own tab named "a.ts vs b.ts" (folders added when both have the same name). Left and right like VS Code.
2. From the Files panel
   - Right-click a file > Select for Compare. Then right-click another file > Compare with Selected (the menu shows the chosen file's name on the right). The chosen file is on the left.
   - Select two files (Cmd+click or Shift+click), right-click > Compare Selected. The first selected is on the left.
   - Folders do not offer these items.
3. From an editor tab: right-click the tab > Compare with Clipboard (clipboard text on the left, the file on the right) or Compare with... (Quick Open opens with "Compare a.ts with..."; pick a file, it goes on the right). Also File > Compare with Clipboard and File > Compare with... and the Command Palette.
4. What the tab shows
   - Unsaved edits: a file open with unsaved changes is compared as it is in the editor; its label says "(unsaved)".
   - Changes on disk show up while the tab is on screen. A hidden tab does nothing until you look at it.
   - A missing file shows as empty with a note ("x does not exist: everything shows as added").
   - Images and PDFs show side by side (same preview as diffs). Other binary files show a note: "The two files are the same." or "The two files differ."
   - Files over 4 MB: "File too large to diff" (same limit as the editor).
   - Open File (toolbar) opens the right file.
5. The clipboard text is kept in memory only while its tab is open; compare tabs do not come back after a restart.

## User page changes: usage/Editing-Code.md (IDE features section)

Add rows/paragraphs:
- Sticky scroll (Settings > Editor > Editing features "Sticky scroll", View > Sticky Scroll). On by default. The first lines of the blocks you are in stay at the top of the file editor, up to five, outermost first. Click a pinned line to jump to it. Blocks come from the language (functions, classes, objects, if blocks...), Markdown uses its headings, plain text and old-style languages use indentation. Only in the file editor (not in diffs or the merge tool).
- Minimap (Settings "Minimap", View > Minimap). Off by default. A small picture of the file beside the scrollbar with the syntax colors; the lighter box is what is on screen. Click to jump, drag the box, or scroll with the wheel over it. File editor only.
- Bracket pair colors (Settings "Bracket pair colors"). On by default. Brackets get a color by nesting depth (three colors that repeat: gold, orchid, blue in dark themes; blue, green, brown in light). A closing bracket with nothing open is red. Strings and comments are skipped. In editors, diffs and the merge tool.
- Highlight matching brackets (Settings "Highlight matching brackets"). On by default; was always on before.

## Developer chapter: developer/How-Compare-Files-Works.md (outline)

1. Why: VS Code and JetBrains compare any two files; the app only compared versions of one file.
2. How it works
   ```mermaid
   flowchart LR
     A[Files panel / tab menu / File menu] --> S[compareStore]
     S -->|openPseudoTab compare-files:...| T[FileCompareTab]
     T -->|sideInput: path or editor text| API[api.compareFiles]
     API --> R[compare_files in git/compare.rs]
     R -->|stat versions equal| N[null: nothing to do]
     R -->|else read, size check, from_bytes| D[FileDiff + version]
     D --> V[DiffView readonly]
   ```
   - Tab path `compare-files:<side>|<side>`: a file side is `f` + encoded absolute path, a clipboard side `c<number>`. Never starts with "/" so it is a pseudo tab (pseudoTabs.ts), closes with the folder of either file (compareTabsInFolder), is not saved in the tab session.
   - Clipboard texts live in compareStore (a Map), freed by prune() when the last tab using one unmounts.
   - A dirty open file sends the editor text (fileCommands.text) with its path for the language name.
   - Refresh: while the tab has a size (ResizeObserver, works with split groups), it reloads when repoStore.fileVersions or workspaceVersion change, when a side's dirty flag flips, and every 2 s while a side has unsaved edits. It passes knownVersion only when the sent texts are unchanged; the backend answers null after two stats.
   ```mermaid
   sequenceDiagram
     participant Tab as FileCompareTab
     participant Rust as compare_files
     Tab->>Rust: left, right, knownVersion
     Rust->>Rust: stat each file (or hash the text)
     alt same version
       Rust-->>Tab: null
     else changed
       Rust->>Rust: size check from metadata, read, from_bytes (imara-diff hunks)
       Rust-->>Tab: FileCompare {diff, version, leftMissing, rightMissing, identical}
     end
   ```
3. Where the code lives: src/lib/compare/compareTabs.ts (paths, labels), compareSelection.ts (menu rules), compareStore.svelte.ts, FileCompareTab.svelte; src-tauri/src/git/compare.rs and commands/compare.rs; Quick Open pick mode in quickOpenStore.svelte.ts (FilePicker) and quickOpenModel.ts (parsePickQuery).
4. Design decisions: size checked from metadata before reading (no 100 MB read for a "too large" answer); a missing file reads as empty rather than an error (it may be created again, the tab follows); folders and relative paths are errors; the version is stat-based like read_worktree_file; a text side's version is its length plus a hash; the binary `identical` flag compares bytes so a non-previewable binary still says same or different; the preview is only offered when both sides are files on disk without unsaved edits.
5. Tests: compareTabs.test.ts, compareSelection.test.ts, quickOpenModel.test.ts (parsePickQuery), menuState.test.ts; Rust git::compare::tests (hunks, unchanged version, text sides, missing, binary and too large, folders and relative paths).
6. Keeping in sync: CompareSide / FileCompare in types.ts mirror git/compare.rs (camelCase).

## Developer chapter: developer/How-Sticky-Scroll-and-Minimap-Work.md (outline)

(Or a section in How-Editor-Features-Work.md if it stays under 1200 words; probably split.)

1. Why: IDE features users expect from VS Code; each a live switch through featurePlan.ts / features.ts compartments.
2. Feature plan: EDITOR_FEATURES gains stickyScroll, minimap, bracketPairColors, matchBrackets. FEATURE_KINDS: sticky scroll and minimap are file only (a diff's two sides share one scroller); bracket colors and matching everywhere. bracketMatching moved from setup.ts into the matchBrackets compartment.
3. Sticky scroll
   ```mermaid
   flowchart TD
     S[scroll event or view update] --> M[requestMeasure read]
     M --> TL[line at scrollTop]
     TL --> C{same top line and doc?}
     C -->|yes| D[reuse lines]
     C -->|no| P1[scopes at top line] --> P2[scopes at the line under the pinned rows]
     P2 --> H[headerLines: outermost first, max 5, lone brace uses the line before]
     D --> W[write: overlay rows, highlightTree spans]
     H --> W
   ```
   - Scopes: syntax tree nodes with foldNodeProp around the top line (a block starting on a ") {" line takes its parent's start); Markdown ATX headings; indentation for no grammar or legacy modes. Scans are capped at 2000 lines.
   - Overlay is a div in view.dom above the scroller (z-index 4), rows with the line number and highlighted text (classHighlighter tok-* classes); horizontal scroll moves only the text. Click jumps with scrollIntoView y "start" and a yMargin of the rows above.
4. Minimap
   - Pure model (minimapModel.ts): layout in lines (folds and wrapping only shift it slightly), slider, click and drag mapping, line runs, paint window.
   - One canvas holds the shown lines plus 100 lines each way; scrolling moves it with a transform; it repaints when the shown lines leave the window, after a theme change, or after an edit at most every 150 ms. Colors come from a hidden probe span with the tok-* class, cached until the theme changes (MutationObserver on the html element and the dark media query).
   - Placement: absolute in view.dom; the scroller gets margin-right 72 px (84 px with the change ruler, which stays at the edge).
5. Bracket colors: candidates are the bracket characters of the visible ranges; a real grammar keeps only nodes named after the character (so strings and comments drop out); the depth at the range start comes from the bracketed ancestor nodes; legacy modes scan 10 000 characters above instead. Colors by depth modulo 3; an unmatched closer uses --tok-invalid.
6. Measurements (20 000-line JS file, Bun, pure parts):
   - bracket colors per viewport (120 lines): about 0.08 to 0.1 ms; after a keystroke 0.2 to 0.3 ms (CodeMirror's own edit plus incremental parse was 0.5 to 0.7 ms on the same machine)
   - sticky scroll per scroll frame (two passes, tree): about 0.01 to 0.03 ms; indentation 0.004 to 0.02 ms; Markdown worst case (no heading within 2000 lines) 0.6 ms, only when the top line changes
   - minimap repaint of the 501-line window: about 1.7 ms before canvas drawing (about 3600 rectangles); scrolling the whole file a quarter line per frame repaints 196 times in 79 800 frames; the slider is a style change
7. Tests: bracketDepth.test.ts, bracketColors.test.ts (JS tree, strings, comments, start depth), stickyScope.test.ts (headers, Allman, five max, two passes, indentation, headings, JS and Python trees, Markdown), minimapModel.test.ts, featurePlan.test.ts, settingsData.test.ts, catalog.test.ts (tokens agree).
8. Bugs we fixed: none yet.
