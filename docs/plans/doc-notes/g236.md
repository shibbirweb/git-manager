## Settings reference lines (Settings page, Git section)

- **Auto fetch** (switch, `autoFetch`, default on): "Fetch every remote in the background while the window is in use, one repository at a time. It never asks for a password; a failed fetch waits longer and shows a note in the status bar."
- **Fetch every** (number, `autoFetchIntervalMinutes`, default 10, 1 to 1440, shown only while Auto fetch is on): "Minutes, from 1 to 1440. The default is 10."
- Both in `~/.gitmanager/settings.json`; bad values fall back (non-number -> 10) or clamp (0 -> 1, 5000 -> 1440).

## User page: usage/Auto-Fetch.md (about 400 words)

- What a fetch is (first use): downloads new commits and branches from a remote without changing your files or branches.
- When it runs: window shown and focused, or focused in the last 10 minutes; online; no other git action running. First fetch about 30 s after opening a workspace, then every interval per repository, one repository at a time with a 5 s gap. Hidden or minimized window: no polling at all.
- What it runs: the same as Git > Fetch All Remotes (`git fetch --all --prune`), quietly. Skips repositories without remotes, during a merge, rebase, cherry-pick, revert or bisect, and while another git command holds `index.lock`.
- Never asks: no password prompt, no askpass window, no Git Credential Manager dialog, SSH runs in batch mode (unless you set your own `core.sshCommand` or `GIT_SSH_COMMAND`). Saved credentials (Keychain, credential helpers, ssh-agent) still work.
- Failures: no error toast. The wait doubles after each failure in a row (10, 20, 40, then 60 minutes max; an interval longer than an hour stays as it is). The status bar shows a small hint: "Fetch needs sign-in", "Fetch offline" or "Auto fetch failed", with a count when several repositories failed ("Auto fetch failed (2)"). Hover lists each repository with git's last error line and "Next try in N minutes. Click to try again now." Clicking retries now.
- Results: ahead/behind in the status bar, the Changes rows and the Git menu (Push N ahead / Pull N behind) update through the normal refresh; the Log shows new remote branches.
- Every fetch is also listed in the Git Console when that is on.
- Screenshots: auto-fetch-settings.png (Settings > Git with the two rows), auto-fetch-hint.png (status bar hint with its tooltip; needs a repo with an unreachable remote).

## User page: usage/Reflog-and-Undo.md (about 700 words)

Reflog:
- Git > Show Reflog opens a tab "Reflog: <repo>" (icon undo). Explain the reflog: git's diary of where HEAD and each branch pointed, kept about 90 days.
- Toolbar: "Reflog of" + a list with HEAD and every local branch; entry count; Refresh.
- Each row: selector (`HEAD@{3}`), commit, action (commit, amend, merge, checkout, reset, rebase, pull, cherry-pick, revert, branch, clone, first commit, other; colored), the message, the time. Long reflogs load 300 at a time while you scroll.
- The selected entry's commit shows below (same details as the Log). Arrow keys move, Enter or double-click opens the commit in a tab.
- Right-click: Show Commit, Copy Revision Hash, New Branch Here..., Checkout Revision (asks first, detached HEAD), Reset Current Branch to Here... (opens the Reset HEAD dialog with that commit filled in).

Undo Last Action (Git menu, after Reset HEAD...):
- Reads the newest reflog entry of HEAD and offers to take it back, asking first with what will happen:
  - commit, cherry-pick, revert: "Undo Commit": back to the parent, changes stay staged, message goes back into the commit box when it is empty.
  - amend: "Undo Amend": back to the commit before the amend, changes stay staged.
  - merge, pull: "Undo Merge" / "Undo Pull": back to before, local changes kept.
  - reset: "Undo Reset": back to where the branch was.
  - checkout: "Undo Checkout": switch back to the previous branch, or check out the previous commit (detached).
  - A branch deleted in this session (newer than the last HEAD move): "Restore Branch".
- Pushed commits: the message adds "It is already pushed, so this rewrites published history." and the button is red.
- Never loses local changes: merge/pull/reset undo uses `reset --keep`; when local changes are in the way it moves the branch with `--mixed` instead and the toast says "local changes kept, files not updated".
- Refused (info toast): during a merge/rebase/cherry-pick/revert ("Finish or abort the operation in progress first"), during a bisect, nothing to undo, the first commit, a rebase or `pull --rebase` ("A rebase cannot be undone here. Use Show Reflog to reset to an older entry.").
- Undo in toasts: after Committed / Commit amended (not when the commit was pushed right away), after Reset (Reset HEAD dialog and the Log), after Checkout Revision in the Log. The toast stays 8 s. It only undoes that action: if something else happened since, "Nothing to undo: The repository changed since then." It asks only when the commit is pushed.
- Delete Branch toast has Restore (recreates the branch at its old commit).
- Screenshots: reflog-tab.png, reflog-menu.png (row context menu), undo-confirm.png (Undo Commit dialog), undo-toast.png (Committed toast with Undo).

## User page: usage/Bisect.md (about 600 words)

- What bisect is: a binary search through history; you mark commits good (works) or bad (broken) and git checks out the next commit to test until it names the first bad one. About log2(n) steps.
- Start: Git > Bisect > Start... picks "Bisect: Pick the Bad Commit" (first item "Current commit (HEAD)"), then "Bisect: Pick a Good Commit" (an older commit without the problem). Toast "Bisect started: test the checked out commit".
- Or from the Log: right-click a commit > Bisect: Mark as Good / Bisect: Mark as Bad (hint "starts a bisect" when none runs). Then mark the other kind.
- Banner (under the header, warning color, bug icon): "Bisecting: about 2 steps left (8 commits to test)" plus "testing <id>", buttons Good, Bad, Skip, Reset. Before both marks: "Bisecting: mark a bad commit" / "mark a good commit" / "mark a bad and a good commit". More than 200,000 candidates: "Bisecting: many commits left to test".
- Found: banner turns green: "Found the first bad commit: <id> <subject>", buttons Show Commit (opens it in a tab) and Reset. Toast "Found the first bad commit".
- Git > Bisect menu: Start..., Mark Good, Mark Bad, Skip, Reset (enabled only while bisecting; Start only when none runs). Command Palette reasons: "No bisect is running", "End the bisect first".
- Log badges: bad (red), good (green), skipped (grey), testing (yellow), "first bad" once found.
- Reset ends the bisect and goes back to the branch it started from ("Bisect ended, back on main").
- Custom terms (`git bisect start --term-new=new --term-old=old` in a terminal) are respected: the banner and badges use them.
- The rest of the Git menu stays usable during a bisect (it is not an operation to continue or abort), but Undo Last Action is off and auto fetch skips the repository.
- Screenshots: bisect-pick.png, bisect-banner.png, bisect-found.png, bisect-log-marks.png.

## Developer chapter: developer/How-Auto-Fetch-Works.md

- Why: ahead/behind and remote branches go stale; JetBrains and VS Code fetch in the background.
- Design decision: the timer lives in the frontend (src/lib/stores/autoFetch.svelte.ts), because it already knows the open repositories, the busy state, the window visibility and focus; the backend keeps no state and no thread (memory rule).
- Mermaid ideas:
  - sequenceDiagram: tick (every 15 s while visible) -> canAutoFetch -> pickDueRepo -> api.autoFetch -> Rust skip checks -> `git fetch --all --prune --quiet` with env -> outcome -> afterFetch -> refreshRepo when fetched.
  - stateDiagram for one repository: Waiting -> Due -> Fetching -> (Fetched|UpToDate|Skipped -> Waiting interval) / (Failed -> Waiting interval * 2^failures, max 1 h).
- Pure rules: src/lib/stores/autoFetchPlan.ts (intervalMs, fetchDelayMs, canAutoFetch, nextFetchAt, pickDueRepo, afterFetch, autoFetchHint). Constants: FIRST_FETCH_DELAY_MS 30 s, REPO_GAP_MS 5 s, RECENT_FOCUS_MS 10 min, MAX_BACKOFF_MS 1 h, TICK_MS 15 s.
- Backend: src-tauri/src/commands/auto_fetch.rs `auto_fetch(repoPath) -> AutoFetchResult { outcome: fetched|upToDate|skipped|failed, skipReason: noRemotes|operation|bisect|busy, errorKind: auth|offline|other, message }`. "fetched" vs "upToDate" compares `refs::fingerprint` before and after. Uses `cli::run_raw_with_env` (new in git/cli.rs).
- Credential-free env: GIT_TERMINAL_PROMPT=0 (always, cli::command), GCM_INTERACTIVE=never, GIT_ASKPASS="" (an empty value also turns off core.askpass and SSH_ASKPASS for git's own prompts; git dies at the prompt before it would ask a helper to erase anything), SSH_ASKPASS="" and SSH_ASKPASS_REQUIRE=never, and GIT_SSH_COMMAND="ssh -o BatchMode=yes -o ConnectTimeout=20" only when the user has no GIT_SSH_COMMAND, GIT_SSH or core.sshCommand.
- Error classification: classify_error over stderr (auth first: could not read username/password, terminal prompts disabled, authentication failed, permission denied, host key verification failed, 401/403...; offline: could not resolve host, couldn't connect, failed to connect, network is unreachable, connection refused, timed out, no route to host).
- Settings: autoFetch, autoFetchIntervalMinutes in settingsData.ts (parsePreferences validates), settings.svelte.ts, SettingsDialog Git section.
- Status bar: StatusBar.svelte `.fetch-hint` button (cloud icon), click = autoFetch.retryNow().
- Started in Workspace.svelte onMount, stopped on unmount; visibilitychange stops the timer while hidden.
- Tests: Rust `commands::auto_fetch::tests` (fetches_new_commits_then_reports_up_to_date, prunes_deleted_remote_branches, skips_repositories_it_should_leave_alone, fails_without_asking_for_a_password with a 127.0.0.1 HTTP server answering 401, reports_an_unreachable_remote_as_offline, classifies_git_errors); Vitest `stores/autoFetchPlan.test.ts`, settingsData "auto fetch preferences".
- Known limit: a user's Pull started while an auto fetch runs may hit a ref lock; the timer never starts while repoStore.busy is set.

## Developer chapter: developer/How-Reflog-and-Undo-Work.md

- Why: the reflog is the safety net of git; Undo turns it into one click.
- Mermaid ideas:
  - flowchart: Undo Last Action -> api.lastAction (HEAD@{0} + branch + pushed + fromBranchExists) + status (op, bisect) + recorded deletion + local branches -> undoPlan -> none (toast) | moveHead(soft|keep) | switchBranch | detach | restoreBranch -> confirm -> run.
  - sequenceDiagram for move_head_back: check HEAD == headId, state clean, commit exists -> `reset --soft` or `reset --keep` -> on failure `reset --mixed`.
- Code: src-tauri/src/git/reflog.rs (classify, checkout_from, full_ref_name, read_page, is_on_remote, last_action; pull --rebase is classified as rebase), src-tauri/src/commands/reflog.rs (get_reflog, last_action, move_head_back, max page 1000), commands/branch.rs (delete_branch now returns the old tip via run_delete_branch), src/lib/views/git/undoPlan.ts (pure), undoActions.ts (recordDeletedBranch, restoreBranch, restoreAction, undoLastAction, undoAction), ReflogTab.svelte + reflogView.ts (labels, visibleRange), stores/gitTabs.ts kind "reflog" (`git-reflog:<repoRoot>`, no file path), GitTab.svelte, EditorTabs.svelte (icon, no Copy Relative Path), ResetDialog `initialRevision` + gitDialogs reset `revision`.
- Toast buttons: repoStore.run gained `action?: (result) => ToastAction | null` and shows toast.successWithAction (8 s). Used in repoActions.commitRepo, ResetDialog, LogView (reset, checkout), sidebar/actions.deleteLocalBranch.
- Design decisions: why a session-only record of deleted branches (the branch reflog is deleted with the branch); why HEAD is checked against the plan (an old toast must not undo something newer); why keep then mixed (never throw away local changes); why soft for commits (matches Undo Last Commit, message back in the box); pushed detection = new commit reachable from any remote-tracking branch.
- Tests: Rust `commands::reflog::tests` (reads_the_reflog_in_pages_newest_first, last_action_knows_the_branch_the_checkout_came_from, last_action_is_pushed_once_a_remote_has_the_commit, undoes_a_commit_softly_and_keeps_its_changes_staged, undoes_an_amend_back_to_the_old_commit, undoes_a_hard_reset_and_a_merge_without_losing_local_changes, refuses_an_undo_once_head_moved_on), `git::reflog::tests`, branch test asserts the returned tip; Vitest undoPlan.test.ts, reflogView.test.ts, gitTabs.test.ts (reflog kind).

## Developer chapter: developer/How-Bisect-Works.md

- Mermaid ideas:
  - sequenceDiagram: Start (pickers) -> bisect_start (`git bisect start <bad> <good> --`, or start then `bisect good` when no bad) -> status fingerprint (hash of BISECT_LOG) changes -> BisectBanner effect -> bisectStore.sync -> bisect_state -> banner text.
  - flowchart of state reading: BISECT_START, BISECT_TERMS, BISECT_LOG ("# first bad commit: [id]", quoted "# first 'bad' commit" in newer git), refs/bisect/bad, refs/bisect/good-*, refs/bisect/skip-*; candidates = revwalk(bad) minus goods minus skipped (capped 200k); steps = git's estimate_bisect_steps.
- Code: src-tauri/src/git/bisect.rs (read, fingerprint, estimate_steps), commands/bisect.rs (bisect_state, bisect_start, bisect_mark uses the BISECT_TERMS words, bisect_reset; refuses options and marks without a running bisect, which would make git prompt), git/status.rs RepoStatus.bisect, git/opstate.rs maps RepositoryState::Bisect to OpKind::None (why: the Git menu must stay usable; bisect has its own banner), watcher already treats BISECT_* as op state.
- Frontend: views/git/bisect.svelte.ts (store per repo, keyed by fingerprint), bisectActions.ts, bisectBanner.ts (pure text + badges), BisectBanner.svelte (mounted in Workspace.svelte under OpBanner), LogView badges and context items, menu ids git.bisect.start/good/bad/skip/reset, menuState (GitRepoInputs.bisecting), registry reasons.
- Tests: Rust `commands::bisect::tests` (finds_the_first_bad_commit_and_resets, starts_without_a_bad_commit_and_marks_by_id_or_skips, marking_needs_a_running_bisect, uses_custom_terms), `git::bisect::tests` (step table, log parsing); Vitest bisectBanner.test.ts.
- Bugs we fixed: **The bisect never named the first bad commit with newer git.**
  - The issue: with git 2.56 (Homebrew), the banner never showed the result, and the Rust test `every_mark_changes_the_status_even_when_head_stays` looped forever in CI (macOS runners use Homebrew git; Apple git 2.50 passed).
  - Why it happened: newer git writes the result line as `# first 'bad' commit: [id] subject`, with the term in quotes; `first_bad_in_log` only matched `# first bad commit: [`.
  - The fix and why: accept both forms (unquoted for older git, quoted for newer) instead of matching git's printed "is the first bad commit" text, since BISECT_LOG is the one place the result is kept. The test loops now stop after 10 marks so a parse failure fails fast instead of hanging CI.
