## Bugs we fixed (drafts)

### How-Changes-and-Commits-Work.md

- **Stage All failed in a folder with tens of thousands of new files.** The user saw "Stage failed: Could not start git add ... Argument list too long" after `npm install` without a `.gitignore`. Why: every path went on the command line (`git add -A -- p1 p2 ...`), and 50k paths are about 1.2 MB, over macOS's 1 MB ARG_MAX (E2BIG). Fix: the paths go to git on stdin with `--pathspec-from-file=- --pathspec-file-nul` (no length limit, and names with spaces, quotes or newlines arrive unchanged). That alone took 65 s for 50k files, because git matches every path against every pathspec, so from 200 paths on the backend folds them into folders when every changed path below a folder is selected (`node_modules/` instead of 50k files): about 6 s, nearly all of it git hashing the files. Chosen over `git update-index --stdin`, which would skip `git add`'s rules (ignored files, embedded repositories), and over a separate Stage All command, because folding also helps any large selection and keeps one code path.

### How-the-Log-Works.md

- **Staging a file reloaded the Log twice.** The user saw the Log flicker and the app use a lot of CPU in big repositories after every stage, unstage or save. Why: the watcher treated `.git/index` like a ref change (`gitDir: true`), and every `run` refresh bumped `historyVersion`, so each stage reloaded the Log twice, each reload up to 10 paged calls that each walked the whole history (0.4 s per reload at 10k commits in a debug build). Fix: the watcher tells refs from the index; `historyVersion` bumps only when the branch tips fingerprint from `get_refs_snapshot` changed; a reload is one call, and `get_log` answers "unchanged" without walking when the tips match. Chosen because the fingerprint is exact (HEAD, branches, remote branches, tags) and costs about 1.4 ms, so even a refresh from an unexpected place cannot cause a walk.

### How-Folder-Watching-Works.md

- **Saving a file read the status twice and re-listed the Files panel twice.** Why: the save path read the status itself and the watcher read it again 300 ms later, and the Files panel reloaded every open folder on any status change and on every content edit (`workspace_changed` was set for every visible work tree change). Fix: a save waits for the watcher's single read (with a 1.5 s fallback when no read happens, ordered by a counter so it can never miss a write), and the Files panel follows `listingVersion`, which moves only when entries are created, deleted or renamed or ignore rules change. Chosen over echo suppression by path, which could hide a formatter rewriting the file right after the save.
- **Bursts refreshed every 300 ms.** During a big checkout or a generated-files burst the app re-read the status (600 ms with 50k untracked files) for every 300 ms batch. Fix: `BurstGate` holds batches once one has more than 1000 paths and sends the merged result after 1 s of quiet or at most every 2 s.

### How-Worktrees-Work.md

- **A git process for the worktree list on every refresh.** Every refs refresh spawned `git worktree list --porcelain` (about 14 ms and one process). Fix: read the worktree admin folders with git2 and std::fs (0.4 ms, no process), checked against the porcelain output in tests for linked, locked, prunable, detached, unborn and bare cases, and only when the refs fingerprint (which covers those admin files) changed.

### Changes view / status (How-Changes-and-Commits-Work.md)

- **Every refresh replaced the status even when nothing changed.** With 50k changed files that is about 6 MB of JSON per read plus every view depending on the status running again. Fix: `get_status` hashes the status (about 30 ms for 50k entries in a debug build, versus 250-420 ms to serialize it) and answers `status: null` for the hash the store holds, so the store keeps the same object.
